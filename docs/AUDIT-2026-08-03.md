Scope: UI, app structure, functionality, and comprehensibility. Evidence from the
code, the live prod database (`qqbecyrhnowmooyjiztz`, org `big-shoulders-restoration-2`),

## Finding 1 — Revision requests strand silently (highest severity)

Three `campaign_asset_revision` tasks queued today are still `queued`:

```
16:21:56  queued  "Add Big Shoulders Restoration truck in the driveway and have team memb…"
16:31:40  queued  "Yes, please change 24/7 line to 773-900-8407. In the future, always us…"
16:37:45  queued  "Our logo needs to be on the truck"
```

**The runner is not down.** `arc_chat_message` tasks created at 16:41 and 17:41 —
*after* all three — completed normally. Chat recovers; revisions do not.

Cause, confirmed in code:

- [src/lib/campaigns/revisions.ts:127](src/lib/campaigns/revisions.ts:127) enqueues
  the row, then calls `notifyArcCampaignTask`. If that wake fails it emits a
  `console.warn` and returns `dispatched: false`. There is no retry.
- [src/lib/arc-chat/inbox.ts:90](src/lib/arc-chat/inbox.ts:90) — the only puller —
  filters `.eq("task_type", "arc_chat_message")`. A `campaign_asset_revision` row
  can never be reclaimed. A missed wake is permanent.
- `dispatched` is returned by both
  [campaigns/[campaignId]/actions.ts:76](src/app/(app)/campaigns/[campaignId]/actions.ts:76)
  and [arc/actions.ts:713](src/app/(app)/arc/actions.ts:713) — and **rendered by
  neither view**. `grep dispatched` in `campaign-detail-view.tsx` and
  `arc/_components/` returns nothing.

So the operator asks for a change, the UI says "revision requested," and three
hours later nothing has happened and no screen says so.

Three fixes, in order of value:

1. Render `dispatched: false` — a "queued, not yet picked up · retry" state on the
   asset card. Cheapest, and it converts a silent failure into a visible one.
2. Widen the `inbox.ts` reclaim filter beyond `arc_chat_message` so a missed wake
   is recoverable rather than terminal.
3. Alert on `agent_tasks` sitting `queued` past a threshold.

Related: `completed_at` is NULL on every `completed` arc_chat_message — only the
cron scan writes it. Task duration is not measurable on the chat path.

## Finding 2 — Brand marks shipped features "Coming soon"

On `/brand`, the "Teach Arc your brand" row has four cards. Two carry a **Coming
soon** badge and swallow the click into a toast:

- **Logo & images** → "Drop logo / photos" is dead
  ([brand-view.tsx:260](src/app/(app)/brand/_components/brand-view.tsx:260))
- **Manual** → "Add a brand note" is dead
  ([brand-view.tsx:265](src/app/(app)/brand/_components/brand-view.tsx:265))

Both capabilities already work, from buttons in the header ~400px above:

- `saveBrandLogo` is imported and called at
  [brand-view.tsx:101](src/app/(app)/brand/_components/brand-view.tsx:101) — that's
  the working **Add logo** button.
- `updateBrandIdentity` is called at
  [brand-view.tsx:435](src/app/(app)/brand/_components/brand-view.tsx:435) — that's
  the working **Edit identity** button.

A user reads "Logo & images: Coming soon" and concludes Arc can't use their logo.
It can. This is the recurring pattern — backend shipped, UI never caught up.

The same `data-soon` mechanism is used honestly elsewhere (8 in Studio, 4 in CRM,
1 in Campaigns, 1 in Analytics). Those look correct; only the two Brand cards
contradict working code.

## Finding 3 — Four names for one state, on one screen

There is a canonical vocabulary — `WORK_STATE_LABEL` in
[src/domain/vocabulary.ts:47](src/domain/vocabulary.ts:47), which says **"Needs you"**.
The campaign detail screen shows four different words for that single state
simultaneously:

- Header pill: **In review**
- Asset card pill: **Needs you**
- Launch readiness panel: **In review**, and **Pending 2**
- The same campaign on the list screen: **Needs you** / "Approve 2 assets"

Remaining hand-spelled sources (excluding tests and demo fixtures):

| Label | Where |
|---|---|
| "Pending approval" | [src/lib/campaigns/read-model.ts:1188](src/lib/campaigns/read-model.ts:1188) + 4 more |
| "In review" | [src/app/(app)/library/page.tsx:62](src/app/(app)/library/page.tsx:62) |
| "Needs review" | [library-view.tsx:793](src/app/(app)/library/_components/library-view.tsx:793) |
| "Ready for review" | [src/lib/arc-chat/launcher-state.ts:64](src/lib/arc-chat/launcher-state.ts:64) |
| "Awaiting approval" | [src/lib/agent-operations/read-model.ts:464](src/lib/agent-operations/read-model.ts:464) |

Route everything through `WORK_STATE_LABEL`. There are already several code
comments documenting prior rounds of this same fix (BSR-656, BSR-659) — a lint
rule banning the literals would stop it recurring.

Also on the campaign detail screen: `0 of 2 approved · 2 pending · 0 live` and
`Approved 0 / Pending 2 / Required 2` are the same three numbers rendered twice,
about 400px apart.

## Finding 4 — "Not configured" reported as a failure

`/analytics` shows a red banner in the backend-less preview:

> **Some analytics couldn't load.** … Opportunity conversion: This data could not be loaded.

Nothing failed. [opportunity-conversion.ts:38](src/lib/performance/opportunity-conversion.ts:38)
returns `{ status: "unavailable" }` when Supabase isn't configured, and
`reasonIfUnavailable` cannot distinguish that from a thrown query — so it renders
the generic failure copy.

[src/lib/observability/unavailable.ts](src/lib/observability/unavailable.ts) warns
against exactly this: *"Not for legitimate non-failures — 'not configured', 'not
found' — which are answers, not outages, and would only train people to ignore the
alert."* Only two call sites do it (`opportunity-conversion.ts`,
`arc-chat/read-model.ts`), and only the first feeds a banner. Small fix; worth it,
because a red banner that cries wolf is how the next real outage gets ignored.

## Finding 5 — Inconsistent honesty labelling on fixture data

`/journeys` carries a **DEMO DATA** badge. Settings uses **"Sample data"** for the
same idea. `/analytics` and `/crm` carry no badge at all while showing `710 leads`,
`$225k won revenue`, `10.7% lead → won`.

That matters beyond tidiness: on `/crm` the KPI strip reads **710 leads** directly
above a Leads tab reading **11**. Anyone demoing the product will hit that
contradiction. One badge component, one label, applied wherever the numbers are
fixtures.

Related, on `/journeys`: the KPI says "Converted — 60% of identified" while the
funnel row for Converted says 75%. Both are defensible (different denominators),
but they sit on one screen using one word.

## What is working well

Worth stating plainly, because a lot of it is better than typical:

- **Plain-English navigation.** "See how it's going / What Arc knows / Make &
  send" — the nav no longer names the codebase. `CLAUDE.md` still documents the
  old "Measure / Intelligence / Create & manage" groups and is stale here.
- **Honest empty states.** `Reply rate —` reads *"Starts once you send your first
  campaign."* `Cost / job —` reads *"Connect an ad account to see this."* That is
  the right answer and it is rare.
- **The Brain page** is the best-explained screen in the app: a "How this works"
  panel, trusted-vs-watching defined in one sentence, and counts that add up
  (33 + 6 + 3 = 42).
- **The approval gate is real and legible.** "Outbound locked", "Nothing sends
  automatically — you confirm each send there", a genuine two-step confirm in the
  Outbox ([outbox-board.tsx:81](src/app/(app)/outbox/_components/outbox-board.tsx:81)),
  and disabled Launch/Download with explanatory tooltips.
- **Opportunities** leads with evidence — "Why Arc flagged this", "What Arc saw"
  with numbered facts, confidence with its inputs spelled out, "Who signs off".
- **Failures are instrumented.** `reportDegraded`, `unavailableRead`, and the
  load-error banners exist specifically so an empty screen can't be mistaken for a
  healthy one. Finding 4 is a misapplication of good machinery, not its absence.

## Is it easy for users to understand?

Mostly yes, with two real obstacles.

**Yes:** the nav, Home checklist, Brain, Opportunities, Outbox, and the approval
language are all written for someone who has never used marketing software. The
`data-soon` toasts and disabled-with-tooltip buttons keep dead ends honest.

**The two obstacles:**

1. **Vocabulary drift** (Finding 3). Four words for one state across the exact
   workflow a new user walks — Campaigns list → campaign detail → Library → Arc
   chat. This is the single largest comprehension tax in the app.
2. **Studio is the outlier.** Four panels and roughly twenty controls — sources,
   compose/generate toolbar, canvas, format chips, layers, version filmstrip, an
   Arc copilot tab — presented at once. Measured against the stated ICP
   (owner-operator local service businesses, `docs/POSITIONING.md`), it reads as a
   design tool rather than "make me an ad." Every other screen leads with one
   obvious next action; Studio leads with a workspace. Worth deciding whether it
   needs a guided default path with the full canvas behind an "advanced" step.

Smaller comprehension snags: Library shows "45 unused" beside a banner reading
"31 approved photos have never been used" (two definitions, one word); the Arc
composer has two adjacent mode pickers ("Work" and "Arc Auto · Spark") with no
explanation of either; the Settings overview KPI strip mixes numbers (`0`, `4`,
`49%`) with a wrapped text phrase ("Waiting for work") in the same slot.

## Suggested order

1. Surface `dispatched: false`, then widen the `inbox.ts` reclaim filter — three
   stranded revisions are live on prod right now (Finding 1).
2. Delete the two false "Coming soon" cards on `/brand` (Finding 2). Fast, and it
   stops the app understating what it can do.
3. Route every approval label through `WORK_STATE_LABEL` and add a lint rule
   (Finding 3).
4. Separate "not configured" from "failed" in `reasonIfUnavailable` (Finding 4).
5. One demo-data badge, applied everywhere fixtures render (Finding 5).
6. Stack the Home checklist rows under ~600px (Finding 6).
7. Decide the Studio question — guided path vs. current canvas.

Not covered here: an authenticated pass over the live prod UI, which needs a human
to sign in. Everything above is from code, the prod database, and the backend-less
preview.
