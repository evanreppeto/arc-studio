# Schema inventory — tables with no code behind them

**Last verified: 2026-08-03** against prod (`qqbecyrhnowmooyjiztz`) and `main`.

Someone reading `supabase/migrations/00000000000000_baseline.sql` today would reasonably
conclude this product has social publishing, ad-spend control, nurture sequences, referral
tokens and personalization rules. It has none of them. The baseline was generated by catalog
introspection from an older database, so it carries every table that project ever had —
including the ones nothing was ever built on.

This file says which is which, so the schema stops implying features that don't exist.

**Nothing here is a deletion list.** Dropping a table is a separate, explicitly-approved
change. Several of these are deliberate forward schema and should stay.

---

## Superseded — the concept exists, under another name

| table | what actually carries it |
|---|---|
| `audits` | `audit_events` — written and read; `audits` has never been referenced |
| `integrity_findings` | `guardrail_findings` — written by `arc-api/draft-review.ts`. See the note below, this one has a twist |
| `task_labels`, `agent_task_label_assignments` | nothing — `agent_tasks` (108 rows) is used without labels, and the label tables have no code |
| `tracking_links` | not a table any more: attribution is stamped inline as UTM parameters on first-party links (`campaigns/external-send.ts`), so there is no row to store |
| `platform_events` | `audit_events` for operator actions, `campaign_events` for campaign activity. `platform_events` predates both |

### The `integrity_findings` twist

`src/domain/integrity-findings.ts` exists, is re-exported from `src/domain/index.ts`, has its
own test file, and is listed in CLAUDE.md as one of the domain modules. All true. But **nothing
imports it** outside its own tests, and the table it was written for has no reader or writer.

It is a complete, tested, unreachable module. Worth knowing before anyone builds on it
assuming it is live — and worth noting that CLAUDE.md's domain list does not distinguish
"implemented" from "reached".

BSR-673 originally named 29 tables. **Two of them were wrong**, and the correction matters

nothing uses them. Zero rows and no code are different facts, and this file exists partly
because they were conflated once already.

## How this was checked, and how the first pass got it wrong

1. Row counts from `pg_stat_user_tables` on prod.
2. For each empty table, grep the repo for the quoted table name across `src/`, `scripts/`,
   `apps/`, then classify each **file** by whether it contains `.insert(` / `.upsert(`.
3. `information_schema.triggers`, to catch tables written by a trigger rather than by code.

**The trap:** the first pass matched only `from("table")` call sites. That misses two very
common shapes — a table name bound to a constant (`const TABLE = "x"`) and helper-based access
(`selectIn(client, "guardrail_findings", …)`). It produced false "dead" findings, including the
two live tables above. Classify at file level, not call-site level, and re-check anything a
grep calls dead before writing it down.

Related: `docs/ORG-SCOPING-AUDIT.md` for the tenancy pass over the same tables.
